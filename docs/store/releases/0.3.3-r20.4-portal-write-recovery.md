# CareSuite HealthOS 0.3.3 – R20.4 Portal-Schreibsitzung

## Produktionsursache

Eine nach einem App-Update wiederhergestellte Portalsitzung konnte noch einen alten Supabase-JWT
verwenden. Die App wirkte angemeldet und konnte gespeicherte beziehungsweise lesbare Daten zeigen,
obwohl der JWT nicht zum Mandanten, Portaltyp oder Mitarbeitendenkonto passte. Dadurch scheiterten
Einsatzaktionen und Nachrichten gemeinsam an den produktiven RLS-Regeln.

Zusätzlich konnten ältere Portalzugänge auf eine fremde oder reguläre Business-Auth-ID zeigen,
während die Edge Function die Sitzung für die synthetische Portal-E-Mail erzeugte. Token und
`employee_portal_accounts.auth_user_id` gehörten dann zu unterschiedlichen Auth-Benutzern.

## Korrektur

- Jeder Portalstart validiert Tenant, Rolle, Portaltyp und Portal-Konto des realen Supabase-JWT.
- Vor Anfahrt, Einsatzaktion, neuer Nachricht und Antwort wird diese Schreibsitzung erneut geprüft.
- Eine veraltete Sitzung wird über `portal-session-refresh` selbstständig erneuert.
- Die Edge Functions akzeptieren nur eine dedizierte Auth-ID mit der erwarteten Portal-E-Mail.
- Falsch verknüpfte Altzugänge werden beim nächsten Login oder Refresh auf die dedizierte Portal-ID
  umgehängt, ohne die normale Business-Identität zu verändern.
- Nutzer-Version ist `0.3.3`; EAS erhöht den produktiven Android-`versionCode` automatisch ab 25.

Es ist keine weitere Datenbankmigration erforderlich. Die bereits produktive Nachrichten-RPC bleibt
unverändert. Employee-Login, Client-Login und Portal-Session-Refresh müssen gemeinsam ausgerollt
werden, bevor der neue AAB verteilt wird.
